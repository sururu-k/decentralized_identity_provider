## 何を解こうとしているか

最上位の脅威は **なりすまし**。IdP が乗っ取られる（あるいは運営者が悪意を持つ）と、
任意のユーザーとしてあらゆる RP で行動できてしまう。
「あなたは確かにユーザーAです」と認定する権限と、それを第三者に証明するアクセストークンを
発行する権限が、どちらも単一主体に集中していることが原因。

派生する問題として、

1. **恣意的なサービス停止** — 運営者の一存で全サービスから締め出せる
2. **利用履歴の集約** — 全リクエストが1箇所を通るので、いつ・どのサービスを使ったかが丸見え

がある。いずれも「権限の一点集中」という同じ根に由来する。

## 前提

**認証だけ分散しても、署名だけ分散してもダメ。**

- パスワード照合を分散しても、JWT 署名鍵が1箇所にあれば認証を飛ばして直接署名できてしまう
- 逆に閾値署名だけ入れても、要求が来たら t 台が素直に署名する作りなら鍵を分散した意味が消える

したがって次の2つが同時に必要になる。

1. 署名鍵がどこにも揃っていない（閾値署名）
2. 認証が通っていないと署名が発火しない

## 現在の方針

2 を **PASTA (CCS 2018)** の方式で実現している。
サーバはパスワードを検証せず、署名シェアをパスワード由来の鍵で暗号化して返す。
正しいパスワードを持つクライアントだけが復号して結合できる。
つまり発火の制御ではなく **復号の可否** で束縛する。

→ 経緯は [prior-art.md](./prior-art.md)、現在地は [status.md](./status.md)

RP から見える形式は標準の OIDC のまま変えず、分散はゲートウェイの内側に隠す。

## スコープ外（要検討）

ノード運営者が結託すれば集権と同じになる、という点。
技術的には [PESTO](https://eprint.iacr.org/2019/1470) の proactive secret sharing に答えがあるが、
運営者の多様性（法域・競合関係）やインセンティブ設計は別途詰める必要がある。

運営コストとユーザー無料の両立（RP がノードを運営する / 暗号経済的インセンティブ /
公共財として運営する / ハイブリッド）も未検討。
