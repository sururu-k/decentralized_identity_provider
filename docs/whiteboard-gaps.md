## 1. 板書が言っていること

**左は PASTA の論文に載っている構成。右はそれを OAuth の形に直す方法。**
左右は同じ主張の言い換えではなく、**問題と解**の関係にある。

### 左：PASTA そのまま — これは OAuth ではない

```mermaid
graph TB
    LB["ブラウザ<br>password 入力"]
    LP["piece に割る"]
    LN1["id: ①"]
    LN2["id: ②"]
    LN3["id: ③"]
    LS["署名<br>（組み上がったトークン）"]
    LB --> LP
    LP --> LN1 & LN2 & LN3
    LN1 & LN2 & LN3 -.->|"しきい値署名"| LS
    LS --> LB
```

出てくるトークンは検証可能だが、**OAuth の流れとしては別物**。足りないものが多い。

| OAuth / OIDC にあるもの | PASTA では |
|:--|:--|
| `/authorize` `/token` `/jwks` `/.well-known` | 無い。独自のプロトコル |
| RP からのリダイレクト、`client_id` / `redirect_uri` / `state` / `nonce` | 無い |
| grant type（`authorization_code` / `refresh_token`） | 無い。一発でトークンが出る |
| アクセストークンとリフレッシュトークンの区別、`scope` | 無い |
| **接続先が1つ** | **クライアントが n 台と直接話す** |

最後の行が特に重い。既存の RP や SDK は「AS は1つの URL」を前提に書かれているので、
**PASTA を持ち込むには RP 側の実装を書き換える必要がある**。
板書の青い矢印「従来の Auth との互換 →」は、その問いを右へ投げている。

### 右：OAuth プロキシで形を戻す

```mermaid
graph TB
    RB["ブラウザ<br>ephemeral key を保持"]
    RX["OAuth プロキシ<br>= 外から見える唯一の AS<br>『こいつが Token を持たない』"]
    RN1["ノード ①"]
    RN2["ノード ②"]
    RN3["ノード ③"]
    RPX["RP"]
    RB -->|"cnf: public key を含む要求"| RX
    RX --> RN1 & RN2 & RN3
    RN1 & RN2 & RN3 -.->|"しきい値署名（暗号化されたシェア）"| RX
    RX -.->|"復号できないまま中継"| RB
    RB -->|"アクセストークン ＋ PoP トークン"| RPX
```

**プロキシは OAuth の図で AS が置かれている場所に、そのまま座る。**
同じエンドポイントを喋り、同じメッセージを返すので、RP からは普通の AS に見える。
違うのは持っている権限だけ。

| | 普通の AS | このプロキシ |
|:--|:--|:--|
| 署名鍵 | 持つ | **持たない**（`s_i` は n 台に散っている） |
| 発行したトークンの中身 | 見える | **見えない**（`ct_i` を復号できない） |
| パスワードの検証 | する | **しない** |
| 乗っ取られたら | 全ユーザーになりすませる | **可用性が落ちるだけ** |

これが「こいつが Token を持たない」の意味。
**AS の位置に居るが AS の権限を持たない** — ここが板書の主張の核心。

> **論文にするならここ。** PESTO は「標準 JWT を出せる」ところまで示しているが、
> **OAuth のエンドポイント形状とメッセージ形状を保つ**という話はしていない。
> 「RP を1行も直さずに差し替えられる AS」は配備の主張で、SSR のような標準化系の会議と合う。
> 詳細は [status.md](status.md) の投稿方針。

**問題は「Token を持たない」がどこまで本当か。** 以下がその検証。

### 穴① オリジン問題 — ログイン画面の JS を配るのは誰か 🚨

**いちばん大きい穴。** 板書には描かれていない。

パスワードは目隠し（blind）してからでないとネットワークに出せないので、
**目隠しの処理はユーザーのデバイス上の JS で走る**。ではその JS を配信するのは誰か。

```mermaid
graph LR
    subgraph Bad["プロキシが配ると"]
        P1["OAuth プロキシ"] -->|"ログイン JS"| B1["ブラウザ"]
        B1 -->|"生のパスワード"| P1
        P1 -.->|"悪意ある JS を1回配るだけで<br>全ユーザーのパスワードが抜ける"| X["閾値化の意味が消える"]
    end

    style X fill:#fdd
```

**信頼の対象が「プロキシは復号できない」から「プロキシが配るコードは正しい」へ移ってしまう。**
これはブラウザ暗号の古典的な問題で、暗号プロトコルの側では塞げない。

想定できる出口は3つ。どれも一長一短。

| 出口 | 内容 | 代償 |
|:--|:--|:--|
| ネイティブ / 拡張機能 | 配信経路をプロキシから切り離す | 「ブラウザだけで動く」を捨てる |
| コード署名 + 透明性ログ | 配布物のハッシュを公開ログに載せ、ブラウザが検証 | ログ基盤が要る。ブラウザ側の検証手段が弱い |
| ノードが各自 JS を配る | t 個のオリジンから取得してハッシュ照合 | ブラウザからは実装しづらい。UX が壊れる |

**PESTO も PASTA もここは扱っていない**（どちらもクライアントを所与としている）。
逆に言えば、ここを正面から扱えば実装寄りの会議では新規性になりうる。

### 穴② `access` の矢印の向き＝「どの OAuth フローか」が未定 🚨

板書では `OAuth プロキシ ---access---> RP` と点線が引かれている。
**これは些細な描き間違いではなく、設計の分岐点をそのまま突いている。**

古典的な OIDC では **RP が OAuth クライアント**で、RP 自身が `/token` を叩いて
認可コードをトークンに交換する。つまり **トークンは AS → RP へ直接流れる**。
板書の矢印はまさにこの形。だが、

```mermaid
graph TB
    A["RP が /token を叩いて<br>コードをトークンに交換する<br>（古典的な認可コードフロー）"]
    A --> B["トークンはプロキシを通って RP へ行く"]
    B --> C["プロキシがトークンを見てしまう"]
    C --> D["『こいつが Token を持たない』が壊れる"]
    style D fill:#fdd
```

プロキシは `ct_i` を復号できないので、**そもそも RP に渡せるトークンを作れない**。
復号できるのはパスワードを持つブラウザだけ。
**だから認可コードフローは、この設計とは構造的に両立しない。**

出口は2つ。

| | 形 | RP から見て | 代償 |
|:--|:--|:--|:--|
| **A. ブラウザがクライアント** | SPA + PKCE + DPoP。RP は resource server に降りる | 標準の OAuth 2.1 | サーバ描画の「◯◯でログイン」が従来通りには作れない |
| **B. `response_mode=form_post`** | ブラウザが組み上げた `id_token` を RP の `redirect_uri` に POST | **標準の OIDC のまま** | `id_token` 中心。アクセストークンは別途 A の形が要る |

**B が本命だと思う。** OIDC の form_post は
「**AS が RP に直接接続せず、ブラウザ経由でトークンを届ける**」ための仕組みで、
今回の「プロキシがトークンを持てない」という制約と正確に噛み合う。
RP 側は `redirect_uri` に POST で `id_token` を受け取り、
JWKS で署名を検証し、`iss` / `aud` / `nonce` を確認するだけ — **完全に標準**。

ただし RFC 9700 は**アクセストークン**を implicit で流すことを禁じているので、
`response_type=id_token` の認証用途に限る必要がある。
API アクセス用のトークンは A の形（PKCE + DPoP）で別に取る、という二階建てになる。

いずれにせよ確定するのは1点。**トークンは必ずブラウザで組み上がり、
ブラウザから RP へ渡る。プロキシは経路に入らない。**

```mermaid
sequenceDiagram
    participant B as ブラウザ
    participant X as OAuth プロキシ
    participant N as ノード群
    participant RP as RP

    RP->>B: /authorize へリダイレクト（nonce, state）
    B->>X: 目隠しした pw, cnf.jkt, nonce
    X->>N: そのまま中継
    N-->>X: b_i, ct_i（h_i で暗号化）
    Note over X: 復号できない。中身は不明
    X-->>B: そのまま中継
    Note over B: 復号・集約してトークンを得る
    B->>RP: form_post で id_token を届ける
    Note over X: ここにプロキシは居ない
```

プロキシは**集約者ではなく中継者**。できることは限られる。

| プロキシにできること | 可否 | 理由 |
|:--|:--:|:--|
| トークンを偽造する | ❌ | 署名鍵シェア `s_i` を持たない |
| トークンを盗み見る | ❌ | `ct_i` を復号できない（パスワードが要る） |
| 可用性を壊す | ⭕️ | ゴミを返せば DoS。ただし検知はできる |
| 誰がログインしたか観測する | ⭕️ | `sub` は見える。ノードも見えるので追加の損失は無い |

脅威は**可用性とプライバシ**であって**不可分性ではない**。

### 穴③ 失敗が観測できないのでレート制限が作れない 🚨

板書の「**ID・PASS は誰が CHECK**」に対する答えは「**誰もしない**」。
これは PASTA のいちばん綺麗なところだが、**副作用が板書に書かれていない**。

```mermaid
graph TB
    A["サーバは検証しない"] --> B["署名シェアを無条件に暗号化して返す"]
    B --> C["成功も失敗も<br>サーバから見て同一の応答"]
    C --> D["『失敗回数』を数えられない"]
    D --> E["失敗 N 回でロックという<br>従来の防御が原理的に作れない"]

    style E fill:#fdd
```

**これは実装漏れではなく、方式の帰結。**
成功と失敗がサーバから区別できないことが安全性の根拠（＝オフライン辞書攻撃を防ぐ）なのに、
同じ性質がレート制限を殺している。

代替は「**試行そのもの**を数える」しかない。

| 方式 | 内容 | 問題 |
|:--|:--|:--|
| 総試行数で絞る | 成否に関わらず `sub` ごとに N 回/時 | 正規利用者も同じ枠を食う。DoS になりうる |
| クライアントに仕事をさせる | proof-of-work / パズル | 攻撃者の方が計算資源を持つ |
| 成功したら本人に通知させる | 事後検知に倒す | 予防にならない |

`status.md` の「レート制限 🔺 構造は得た」は**楽観的すぎる**ので、ここを根拠に下方修正すべき。

---

### 穴④ 「PoP トークン」は静的な1枚ではない 🔧

板書は「アクセストークン ＋ PoP トークン」を並んだ2枚の箱として描いているが、
DPoP（RFC 9449）では PoP 側は**リクエストごとに新しく作る証明**。

| | 実体 | 寿命 |
|:--|:--|:--|
| アクセストークン | ノードが閾値署名した JWT。`cnf.jkt` を含む | 5 分（`TOKEN_LIFETIME`） |
| DPoP proof | ブラウザが ephemeral key で**毎回**署名する JWT。`htm` / `htu` / `iat` / `ath` を含む | 1 リクエスト |

用語だけのズレで設計は壊れていないが、**「持ち回るもの」と「都度作るもの」を混ぜると
ephemeral key の保管要件（穴⑦）を見誤る**ので分けて書く。

### 穴⑤ REFRESH!? — ここだけは原理的に無理 ⚠️

板書の右下、赤字級に大きく書かれている箇所。設計自体は `refresh-token.md` で済んでいる
（`h_i` の代わりに sign-on 時に配った `rs_i` で開ける）。**残っているのは再利用検知**。

```mermaid
graph TB
    G["RFC 9700 §4.14<br>公開クライアントの refresh token は<br>sender-constrained または rotate"]
    G --> R["rotate するなら<br>『使い回し』を検知する必要がある"]
    R --> Q["検知には全ノードが<br>同じ『使用済み』集合を見る必要がある"]
    Q --> I["定足数 A と B の交差の大きさは<br>A ∩ B ≥ 2t − n"]
    I --> J["t−1 台の腐敗下で交差に正直者を保証するには<br>2t − n &gt; t − 1 → t ≥ n"]
    J --> K["t &lt; n では保証できない"]

    K --> S1["逃げ道① sender-constrained だけで通す<br>RFC 9700 は OR 条件"]
    K --> S2["逃げ道② 合意層を足す<br>t &lt; n を諦めない代わりに複雑さが増える"]

    style K fill:#fe8
```

**この不可能性が、いまのところ一番論文になりそうな部分**（`status.md` の投稿方針を参照）。
穴として塞ぐより、**結果として書く**方が価値がある。

### 穴⑥ `sub` / `aud` はノードから見える 🔧

Issue #81 の「問題②（プライバシ）」は**未解決のまま**。
板書では触れられていないが、ノードは署名対象の平文を見るので、
**誰がどのサービスにログインしたかがノードに漏れる**。

閾値化しても隠れない。隠すには盲目署名か、`sub` を per-`aud` の擬似 ID にする必要がある。
後者は決定的な導出で足りるが、RP をまたいだ名寄せができなくなる副作用がある。

---

### 穴⑦ ephemeral key の寿命と保管 🔧

板書は鍵アイコンだけで、どこに置くかが描かれていない。ここが決まらないと穴⑤も決まらない。

| 選択肢 | 抽出耐性 | タブを閉じたら | リフレッシュとの相性 |
|:--|:--|:--|:--|
| WebCrypto non-extractable + IndexedDB | ⭕️ JS から取り出せない | 残る | ⭕️ 良い |
| メモリのみ | ⭕️ | 消える | ❌ 毎回ログインし直し |
| localStorage に生の鍵 | ❌ XSS で抜かれる | 残る | DPoP の意味が消える |

**推奨は non-extractable + IndexedDB。** DPoP の前提（鍵をエクスポートできない）を満たす唯一の現実解。
